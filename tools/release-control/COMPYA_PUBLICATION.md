# 컴프야 기존 후보의 암호화 승인 게시

제품 빌드·실행·설치와 게시를 분리한다. 새 빌드는 비공개 요청 경로에서 명시 요청 시에만 수행하고, 이 제어기는 검증된 동일 ZIP만 게시한다. main의 과거 앱 코드로 빌드하지 않는다. 워치나 다른 앱 경로를 사용하지 않는다.

## 요청과 전달

정확한 앱·대상·버전·전체 소스 SHA·run/artifact ID·외부/내부 파일 해시·검사 결과·현재 공개 Release ID를 제시하고 그 버전의 게시 승인을 받은 뒤, 에이전트가 기존 소유자 전용 #3에 원본 댓글을 등록한다.

`/compya-publish approve REQUEST_ID SOURCE_SHA VERSION OUTER_ZIP_SHA256 BASELINE_RELEASE_ID sealed-v1`

공개 댓글에는 임시 파일 주소를 넣지 않는다. 주소를 넣는 예전 형식은 거부한다. 사용자에게 다운로드·압축·암호화·업로드·PC 명령을 요구하지 않는다.

게시기는 원본 승인과 첫 실행·활성화·고정 제어기 SHA를 확인한 뒤 메모리 안에서만 일회용 암호화 수신자를 만든다. 공개 확인 자료는 bot 댓글에 남기고, 에이전트가 native 실행·소유자·고정 workflow/제어기·실행 ID·승인 원문 해시·만료를 대조해 동일 후보의 파일 주소를 RSA-OAEP-SHA256 + AES-256-GCM으로 암호화한다.

전달 형식은 `/publication-file-deliver compya REQUEST_ID PUBLISHER_RUN_ID ENVELOPE_JSON`이다. 180초 수신 창 안의 원본 소유자 전달 1개만 받는다. 앱·실행·후보·승인 맥락 불일치, 편집·중복·변조·만료·철회는 거부한다. 복호화한 주소는 Node/Python 사이 비공개 pipe로만 전달하며 명령 인자·로그·파일에 남기지 않는다. 종료 후 수신자의 개인 부분을 보관하지 않는다.

새 계정·PAT·장기 암호화키·서명키·GitHub secret을 등록하거나 바꾸지 않는다. 기존 GITHUB_TOKEN을 같은 저장소에만 사용하며 공개 확인 댓글에 필요한 issues 쓰기만 게시 workflow에 추가한다. 다른 비공개 저장소의 권한을 가져오지 않는다.

## 유지하는 검사와 실패 처리

원래 소유자 승인·15분 유효기간, 버전 증가·기존 태그/draft·현재 공개 기준·ZIP 해시·Windows 실행파일 형식·개인 설정/로그 차단을 유지한다. 앱을 재빌드하거나 실행하지 않는다. 부분 실패와 모호한 결과는 자동 재시도·덮어쓰기·삭제로 해결하지 않는다. 게시와 실제 기기 업데이트·게임 실행은 별개다.

기존 검사 CLI의 영수증 생성은 승인 게시 과정의 일부다. 실제 후보에 대해 합성 승인 이벤트를 만들어 실행하거나 그 결과를 실제 승인으로 사용하지 않는다. 가짜 데이터의 임시 검사 결과와 실제 게시 결과를 구분한다.

## 반영과 검증 범위

이 파일을 포함한 제어기 소스는 지정된 개발 브랜치의 검증·업로드 절차로 준비한다. 운영 게시기는 별도 검토 workflow가 정확한 제어기 commit을 고정 참조하고, 그 변경의 승인을 받아 반영하기 전에는 바뀌지 않는다. 제품 소스 변경을 운영 main으로 함께 병합하지 않는다.

- Python 제어기: `python -B -m unittest discover -s tools/release-control -v`
- 암호화 전달: `node --test tools/release-control/test_sealed_file_transfer.mjs`

합성 검사·소스 동기화는 실제 온라인 전달·후보 빌드·게시·설치·실게임·Authenticode 검증을 증명하지 않는다. 기존 2.0.29 후보와 별도 개발 2.0.30을 혼동하거나 자동 선택·빌드하지 않는다.
